## 2. The event types (610, shared with 611 and 614)

Mirror what 609 now publishes. **Consumers ignore unknown fields** —
`FAIL_ON_UNKNOWN_PROPERTIES = false`. This is the opposite of `trade-api`'s
HTTP setting, deliberately: a Kafka consumer that throws on a new field turns
an additive change into an outage.

```java
record EventEnvelope<T>(String eventId, String eventType, Instant eventTime,
                        String source, int schemaVersion, T payload) {}

record OrderPlacedPayload(String orderId, Long accountId, String symbol,
                          OrderSide side, BigDecimal quantity, BigDecimal price,
                          String status, Instant createdOn, String idempotencyKey,
                          Long instrumentId) {}
```

`instrumentId` is on the wire but **we do not branch on it** — it is an
internal key. We resolve the instrument from Postgres when we load the order.

## 3. The quote client (610)

`GET /v1/quotes/{symbol}`, header `X-Api-Key`. Base URL from
`FAUXNANCE_BASE_URL`, key from `FAUXNANCE_API_KEY`. **The key appears in no
properties file, no YAML and no Java constant** — environment only.

```java
public interface QuoteSource {
    Quote quote(String symbol) throws QuoteUnavailableException;   // single, fill path
    Map<String, Quote> quotes(List<String> symbols);               // batch, poller
}
```

`Quote` carries `price, bid, ask, spreadBps, currency, change, changePercent,
previousClose, asOf, marketState, stale, source` — mapped from `data` plus
`meta.stale` and `meta.source`.

**Careful:** on the single-quote response `stale` is in `meta`; in the batch
response it is at **item** level. Two mappings, one `Quote` type.

### Retry policy — settled

Retry **only** on these, bounded at 3 attempts with exponential backoff:

| Condition | Why |
|---|---|
| Connection error / timeout | transient |
| `429` | honour the `Retry-After` header rather than a blind backoff |
| `503 UPSTREAM_UNAVAILABLE` | transient |
| `202 BACKFILL_IN_PROGRESS` | no price *yet* |
| `meta.stale == true` | upstream unreachable, we are being handed an expired price |

**Do not branch on `source`** (`stored` / `cache` / `synthetic` / `upstream:*`)
and **do not branch on `marketState`**. Team decision, and the evidence backs
it: `bid`/`ask` are *always* modelled (`spreadSource` has one value), and Indian
symbols return `marketState: "unknown"`. Branching on either would be inventing
a rule out of noise.

Budget spent, or a `404 SYMBOL_NOT_FOUND` (not retryable) → throw
`QuoteUnavailableException` → the order is **rejected** with `NO_PRICE`. Never
dead-lettered: a price feed being down is a business outcome, and dead-lettering
would leave the order at `NEW` for ever.

### Tests (WireMock)
- [ ] a 200 maps every field, including `meta.stale` and `meta.source`
- [ ] `stale: true` retries, then succeeds on a fresh second response
- [ ] `stale: true` on every attempt exhausts the budget and throws
- [ ] `429` waits the `Retry-After` value, then succeeds
- [ ] `503` retries, then succeeds
- [ ] `202` retries, then succeeds
- [ ] `404` throws immediately, no retry
- [ ] the API key travels in `X-Api-Key` and appears in no log line
- [ ] batch: item-level `stale` maps correctly; a per-symbol `error` entry does
      not fail the whole batch

## 4. The fill rule (610) — the centre of the story

Pure. No database, no socket. That is the only reason its interesting cases
actually get tested.

```java
sealed interface FillDecision {
    record Fill(BigDecimal executedPrice) implements FillDecision {}
    record Reject(RejectReason reason)    implements FillDecision {}
}

public interface FillRule { FillDecision decide(OrderSnapshot order, Quote quote); }
```

**The rule itself — marketability only:**

> BUY fills when `limitPrice >= ask`, at `ask`.
> SELL fills when `limitPrice <= bid`, at `bid`.
> Otherwise `PRICE_NOT_MET`.

You buy at `ask` and sell at `bid`. Settling both sides at `price` makes a buy
followed by a sell cost nothing, so any strategy that trades often looks free
when it is not. The spread is the cost of trading — charge it.

**Rounding, settled:** round `bid`/`ask` to **4 decimal places, HALF_UP** —
the width of `orders.fill_price` — **before** the comparison, and store that
same rounded value. Compare and store the same number, or an order can fill at
a price that failed its own check.

**Two strategies behind one interface**, selected by asset class:
`EquityFillRule` (above) and `MutualFundFillRule` (always
`INSTRUMENT_NOT_PRICEABLE`). A mutual fund has no bid and no ask — it is not
price-discovered on an order book — so the rule has nothing to evaluate. Adding
an instrument class later is a new strategy, not an edit to this one.

### The check order — decided, and worth defending

`PreTradeChecks`, also pure, runs **before** the quote is fetched where it can:

1. instrument not tradable → `INSTRUMENT_NOT_TRADABLE`
2. no two-sided market, i.e. mutual fund → `INSTRUMENT_NOT_PRICEABLE`
3. account not `ACTIVE` → `ACCOUNT_NOT_ACTIVE`
4. — *fetch the quote here* —
5. fill rule → `PRICE_NOT_MET`
6. BUY: re-check funds **at the executed price** → `INSUFFICIENT_FUNDS`
7. SELL: re-check holdings → `INSUFFICIENT_HOLDINGS`

Steps 1–3 come first because they spend no quota. An order we already know we
will reject should not cost one of 2000 daily requests.

Steps 6 and 7 are Sprint 5 rules 6 and 7, **re-checked here** because both
moved while the order sat on the topic: the balance has changed, and the price
is now the executed price rather than the limit. Suspension is re-checked
because an account suspended after acceptance should not trade, including on
orders accepted before the suspension.

### Tests — the required paths, plus boundaries
- [ ] a BUY limit **above** the ask fills at the ask
- [ ] a BUY limit **exactly equal** to the ask fills at the ask
- [ ] a BUY limit one tick **below** the ask is `PRICE_NOT_MET`
- [ ] a SELL limit **below** the bid fills at the bid
- [ ] a SELL limit **exactly equal** to the bid fills at the bid
- [ ] a SELL limit one tick **above** the bid is `PRICE_NOT_MET`
- [ ] a quote needing rounding fills at the rounded price, and that same price
      is the one compared
- [ ] an execution-time re-check rejects a BUY the account can no longer afford
- [ ] a SELL whose holding shrank is `INSUFFICIENT_HOLDINGS`
- [ ] an account suspended after acceptance does not trade
- [ ] a non-tradable instrument is rejected without fetching a quote
- [ ] a mutual fund is `INSTRUMENT_NOT_PRICEABLE` without fetching a quote
- [ ] an order with no available price is resolved, not left at `NEW`

## 5. Consumer + orchestration (610)

`OrderPlacedConsumer`, group **`trade-executor`** — fixed by contract.
`enable.auto.commit=false`, manual ack.

What it does with one order:

1. consume `ORDER_PLACED`
2. load the order from Postgres — **status other than `NEW` means a previous
   delivery already settled it**: acknowledge, publish nothing
3. load instrument, account, position
4. `PreTradeChecks` steps 1–3
5. fetch the quote
6. `FillRule`
7. `SettlementPort.settle(...)`
8. acknowledge

Step 2 is a cheap early exit; the real duplicate guard is the conditional
`UPDATE` in step 7, which holds under concurrency because the database
serialises the two updates.

### The seam for 611 — interface fixed, implementation thin

```java
public interface SettlementPort {
    SettlementResult settle(FillDecision decision, OrderSnapshot order);
}
public enum SettlementResult { SETTLED, ALREADY_SETTLED, LOCK_EXHAUSTED }
```

610 ships `GuardedSettlement` doing **only** the conditional update:

```sql
UPDATE orders SET status = ?, fill_price = ?, resolved_at = ?, rejection_reason = ?
 WHERE order_id = ? AND status = 'NEW'
```

Zero rows → `ALREADY_SETTLED`. Publish nothing, acknowledge, **log it clearly**
— that log line is what story 612 points at during the demo.

Status and `resolved_at` must be set in the same statement, or
`ck_orders_resolved_at_matches_status` rejects the write.

**611 replaces the implementation, not the interface** — adding cash, position,
the optimistic-lock retry and the `trade-events` publish.

### Tests
- [ ] an `ORDER_PLACED` for a `NEW` order runs the full path and settles
- [ ] a second delivery of the same message settles nothing and publishes nothing
- [ ] an order already `FILLED` in Postgres is acknowledged, not reprocessed
- [ ] integration: against a mocked quote source covering a fill, a reject, and
      a pricing-unavailable response

## 6. Market-data poller (614)

Scheduled component **inside the executor**, own package. Not a second service,
not a second container, not a second runtime. One component calls Fauxnance, so
one component holds the key and one component divides the budget.

It is **not on the order path**: it does not poll because an order arrived, and
the consumer never waits for a poll.

### Symbol set
Distinct tradable symbols someone holds or has working: `position` ∪ orders at
`NEW`, **excluding mutual funds** — polling an MF would spend quota on a
guaranteed 404.

### Interval floor — enforced in code, not documented and hoped for

Not a constant. The floor is computed from the symbol count, because batching
caps at 25 per request:

```
callsPerCycle = ceil(symbolCount / 25)
callsPerDay   = (86400 / intervalSeconds) * callsPerCycle
require: callsPerDay <= DAILY_QUOTA - FILL_RESERVE
```

With `DAILY_QUOTA = 2000` and `FILL_RESERVE = 200`, ≤25 symbols at 60s gives
`1440 <= 1800` ✓. At 30s it is `2880 > 1800` ✗ and the interval is clamped up,
with a warning naming the arithmetic.

Implemented via `SchedulingConfigurer` rather than a `@Scheduled` annotation,
so the clamp is real code that a test can drive.

`POLL_INTERVAL_SECONDS` is read from the environment. Default and floor 60.

### Publishing
**One Kafka message per symbol**, keyed by `symbol`, `source = "market-poller"`.
Never one per batch: batching the HTTP call is a quota optimisation and it is
correct, but batching the Kafka message puts several symbols behind one key and
destroys the per-symbol ordering the contract promises.

### Liveness
A scheduled method that throws is not necessarily rescheduled, and a poller
that quietly stopped inside a running container is harder to notice than one
whose container exited. Catch at the top of the poll, log, and let the next
tick proceed.

### Quota arithmetic — record it in `design/`
60s interval, ≤25 symbols, 1 call per cycle → **1440 requests/day**, leaving
**560** of 2000 for the fill path. At 30s it would be 2880 and the key is gone
by mid-afternoon. Eight symbols fetched one at a time every 30s would be 23040
and the key is gone in two hours.

### Tests
- [ ] 25 symbols are fetched in **one** request
- [ ] 26 symbols become two requests, 25 + 1
- [ ] each quote publishes its own message, keyed by its symbol
- [ ] a batch of N symbols publishes exactly N messages, never 1
- [ ] the configured interval is accepted when it fits the daily quota
- [ ] an interval below the computed floor is clamped, with the arithmetic logged
- [ ] mutual funds are excluded from the poll set
- [ ] a throwing poll does not stop the schedule

## 7. Shared quota counter (610 + 614)

One counter, both callers, resetting at 00:00 UTC — the contract asks for
"one place that counts what has been spent". The poller stops at
`DAILY_QUOTA - FILL_RESERVE` so it can never starve the fill path; the first
symptom of getting this wrong is orders rejected because no price could be
obtained.

`GET /usage` costs a quota unit itself, so it is used for reconciliation on
startup and hourly — never per poll cycle.

### Tests
- [ ] both callers increment the same counter
- [ ] the poller stops at the reserve boundary; the fill path still gets quotes
- [ ] the counter resets at 00:00 UTC
