    Overview

    Platform overview

    Source: README.md

    Capstone project, SE3 Team 2. YELLOW is a stock and mutual-fund trading platform for Indian customers (INR only). A customer applies for an account, passes KYC, activates a login from an email, adds cash, and buys and sells. Sprint 10 added six extensions: preferences, notifications, watchlists and price alerts, portfolio and P&L, trade advice, and automated strategies.

    The documents use ASD-STE100 (Simplified Technical English): short sentences, active voice, one word for one thing.

    Architecture in one picture

    Three ideas hold the design together:

    1. Accept fast, execute later. The Trade REST API validates and records an order, then puts it on Kafka. The Trade Executor prices and settles it.
    2. At-least-once delivery, idempotent consumers. Kafka can deliver a message two times. Each consumer is safe when that occurs.
    3. The database is the last guard. CHECK constraints, unique keys and UPDATE ... WHERE status = 'NEW' stop bad states.

    The full diagram with function calls is in docs/architecture/system-architecture.md.

    6. Design rules that hold the system together

    1. Accept fast, execute later. OrderService.placeOrder() validates and records. The executor prices and settles later.
    2. At-least-once delivery, idempotent consumers. Kafka can deliver a message two times. Each consumer is safe when that occurs.
    3. The database is the last guard. CHECK constraints, unique keys and UPDATE ... WHERE status = 'NEW' stop bad states.
    4. The token decides the account. Each route compares the path account with the accountId claim. A mismatch gives 403 ACC-403.
    5. Transactional outbox for KYC_VERIFIED, ACCOUNT_PROVISIONED and ORDER_CANCELLED. The event commits with the change.

    Notifications module (Sprint 10, extension 2 of 6, mandatory)

    Source: services/trade-api/src/main/java/com/yellow/trade/notifications/README.md

    Watchlists and price alerts module (Sprint 10, extension 3 of 6, mandatory)

    Source: services/trade-api/src/main/java/com/yellow/trade/watchlists/README.md

    Package com.yellow.trade.watchlists. The module keeps a customer's watchlists on the server, stores the last price of each instrument from market-data, and fires price alerts.

    Sequence diagrams: 04-watchlist.md and 07-price-alerts.md.

    What it does

    • Watchlists: create, rename, delete. Add and remove instruments. Each item shows the last price, the day's change and a stale flag.

    • Consumes market-data. For each quote: keep the newest price, then fire the crossed alerts in one transaction with the notification (decision 0008).
    • Owns the view watch_polled_symbols. The executor's poller reads it, so watched stocks get prices (decision 0009).

    Trade advice module (Sprint 10, extension 5 of 6, stretch)

    Source: services/trade-api/src/main/java/com/yellow/trade/advice/README.md

    Package com.yellow.trade.advice. The module gives a BUY, SELL or HOLD signal for a stock, with the figures behind it. It uses one methodology: 20-day SMA against 50-day SMA, confirmed by RSI(14). Every answer says: "Information, not advice. Computed from delayed educational data; past prices do not predict future ones."

    Sequence diagram: 08-signals.md.

    What it does

    • GET /api/v1/advice/{symbol}: the signal for one stock.
    • GET /api/v1/accounts/{id}/advice: a signal for each stock the customer holds or watches, holdings first, at most 30 (decision 0016).
    • Keeps signals in memory. There is no table (decision 0015).
    • Computes a signal the first time someone asks. Then AdviceRefreshJob computes it again every 5 minutes. A symbol nobody asks for in one day is forgotten.
    • Reads the latest price from market-data into memory (LatestPrices). Today's live price counts as today's close.
    • A fund, an unknown stock, or a stock with no chart gives "no signal". It never gives a guess.

    12. A08:2021 Software and data integrity failures

    Risk. A forged or replayed message makes the system act: provision a login, fire an alert, book P&L, place an order.

    Controls

    • Transactional outbox for KYC_VERIFIED, ACCOUNT_PROVISIONED, ORDER_CANCELLED. Only a committed change is announced (outbox/OutboxRelay.java:60).
    • Idempotent consumers. Each consumer has a unique key or a guarded update. A replay does nothing.
    • Portfolio checks the source. RealisedBook.book() books only if orders holds a FILLED SELL for that account (portfolio/RealisedBook.java:58). A forged event books nothing.

    Kafka is PLAINTEXT with no ACLs (U6). Fix for a real deployment: TLS and SASL/SCRAM, per-topic ACLs (only the Trade API writes orders, only the poller writes market-data).

    Recall cards

    Read the question, answer it aloud, then open the card.

    01Which three ideas hold the design together?

    Accept fast, execute later. At-least-once delivery with idempotent consumers. The database is the last guard (CHECK, UNIQUE, guarded UPDATE).

    02What are the ports?

    UI 4200, Trade REST API 8085, Trade Executor 8081, Auth 3000, Postgres 5432, Kafka 9092 (29092 inside Docker).

    03Why key the orders topic by accountId?

    Kafka keeps order only inside one partition. A SELL must come after the BUY that funded it.

    04Why is ORDER_PLACED published AFTER_COMMIT?

    Inside the transaction it can announce a rollback. After commit a lost event can be replayed from the orders table. Known gap U1: move it to the outbox.

    05What makes a duplicate ORDER_PLACED harmless?

    FullSettlement.settle() runs UPDATE orders ... WHERE status = NEW. The second delivery gets 0 rows: ALREADY_SETTLED, nothing moves, nothing published.

    06What are the 8 domain order rules?

    1 account exists, 2 ACTIVE, 3 KYC VERIFIED, 4 instrument exists and tradable, 5 quantity and price > 0, 6 BUY funds, 7 SELL holdings, 8 idempotency key unused.

    07How do BUY and SELL differ at accept time?

    BUY: rule 6 and blockFunds() reserves qty x limit. SELL: rule 7 checks the position; nothing is reserved (gap U3).

    08Which events use the transactional outbox?

    KYC_VERIFIED (trade-api), ACCOUNT_PROVISIONED (auth), ORDER_CANCELLED (trade-api).

    09How does a customer get a login?

    Apply -> KYC job VERIFIED -> outbox -> kyc-events -> auth provisions -> account-provisioning -> ActivationService mints a token over /internal/activation-tokens -> email -> /activate registers with the token.

    10Why does a duplicate application return 202?

    A different answer would tell an attacker that a PAN or email belongs to a customer.

    11What stops customer A reading customer B?

    AccountAccess.requireOwn(): path account vs token accountId claim, 403 ACC-403 logged, before any read.

    12What are the two Java seams between modules?

    preferences.api.ChannelResolver (used by notifications) and notifications.api.AlertDelivery (used by watchlists). Also Holdings and WatchedInstruments for advice.

    13Why are seams Java interfaces, not HTTP routes?

    A route that does not exist cannot be called with a stolen customer token.

    14Why does notifications use a ledger?

    A slow mail server must not stop a Kafka partition. The offset commits when the row is QUEUED. A separate thread sends.

    15Why UNIQUE NULLS NOT DISTINCT (event_id, alert_id)?

    One quote can cross many alerts. A key on event_id alone keeps only the first. NULLS NOT DISTINCT keeps trade events unique on event_id.

    16When is the alert channel decided?

    At send time: NotificationDispatcher.send() calls ChannelResolver.resolve(). A change in Settings applies to queued messages too.

    17Why does an alert fire only once?

    Firing on each quote past the level floods the inbox. The customer re-arms it (decision 0007).

    18Why Propagation.MANDATORY on AlertDelivery.deliver()?

    An alert must never read TRIGGERED with nothing queued. A call with no transaction is refused.

    19What are the watchlist caps?

    5 watchlists, 50 items each, 20 active alerts, 10 strategies. 409 LIM-409, counted under pg_advisory_xact_lock.

    20How is realised P&L booked?

    RealisedBook.book() on each SELL ORDER_FILLED, only if orders holds a FILLED SELL for that account. (sale - avgCost) x qty, CHECK in the table.

    21What is the advice rule?

    SMA20 vs SMA50 gap, confirmed by Wilder RSI(14). Gap under 0.25 % = HOLD. Up and RSI < 70 = BUY. Down and RSI > 30 = SELL. Always with the disclaimer.

    22How does a strategy place an order with nobody signed in?

    StrategyTokenClient mints a 300 s token at /internal/strategy-tokens (x-internal-secret). HttpOrderPlacer calls POST /api/v1/orders with it.

    23What bounds a strategy?

    maxSpend per firing, maxPosition after the buy, stop after 3 failures, unique run on (strategy_id, source_event_id), idempotency key strategy-{id}-{eventId}.

    24Which consumer groups start at latest, and why?

    notification-service and strategy-service: old trades must not be mailed, old quotes must not spend money. portfolio-service starts at earliest: booking old sales is safe.

    25What happens to a refresh token used twice?

    Theft alarm: every refresh token of that credential is revoked and SECURITY_REFRESH_REPLAY is logged and paged.

    26Name the OWASP open items.

    A05 no HTTP security headers on JSON APIs. A06 NestJS 11 upgrade (10 prod advisories in auth). A07 no logout / access-token revocation. A08 Kafka has no auth.
